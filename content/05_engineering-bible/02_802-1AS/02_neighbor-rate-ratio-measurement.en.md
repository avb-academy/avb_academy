{{% notice info %}}
- The `neighborRateRatio` describes how fast the clock of the link partner runs relative to the local clock.
- The value is used to compensate frequency differences between neighboring time-aware systems.
- Even very small oscillator deviations accumulate into significant timestamp errors over time.
- The `neighborRateRatio` is continuously estimated using successive `Pdelay_Resp` messages.
{{% /notice %}}

The propagation delay measurement described in [Propagation Delay Measurement](01_propagation-delay-measurement.md), assumes that both communication partners measure time using clocks that advance at the same rate.

In real systems this assumption is not true.

Every device contains its own oscillator, and no two oscillators run at exactly the same frequency. Even high quality oscillators typically differ by several {{< tooltip "ppm">}}. Consider two devices, each with its own oscillator: 

- Device A oscillator: {{< imath >}} 125.000000MHz {{< /imath >}}
- Device B oscillator: {{< imath >}} 125.000125MHz {{< /imath >}}

Although the difference appears very small, the resulting timestamp error continuously accumulates over time. If both devices receive a message and need to timestamp them upon arrival, slightly more time has passed on Device B than on Device A. Making the event that physically occurs at one point in time being observed at two different devices times.

The `neighborRateRatio` calculation compensates for this effect by estimating how fast the neighbor clock runs relative to its own the local clock.

## Definition of neighborRateRatio

{{% notice info %}}
Sec. 10.2.4.6, Sec. 14.6.10
{{% /notice %}}

The `neighborRateRatio` describes the measured ratio between the frequency of the clock of entity at the time-aware system at the other end of the link, and the frequency of the local entity.

Conceptually, the value can be written as:

{{< math >}}
neighborRateRatio =
\frac{f_{\text{neighbor}}}{f_{\text{local}}}
{{< /math >}}

where:

- {{< imath >}} f_{\text{neighbor}} {{< /imath >}} is the neighbor clock frequency
- {{< imath >}} f_{\text{local}} {{< /imath >}} is the local clock frequency

The value therefore indicates whether the neighbor clock runs:

- equally fast. Then the ratio is {{< imath >}} 1.0 {{< /imath >}}
- faster. The ratio is greater than {{< imath >}} 1.0 {{< /imath >}}
- slower. The ratio is smaller than {{< imath >}} 1.0 {{< /imath >}}

For example, {{< imath >}} neighborRateRatio = 1.000001{{< /imath >}} means that the neighbor clock runs approximately {{< imath >}} 1ppm {{< /imath >}} faster than the local clock.

## Computation Process

{{% notice info %}}
Sec. 11.2.15.2.3 
{{% /notice %}}

The `neighborRateRatio` is estimated using timestamps conveyed by successive `Pdelay_Resp` and `Pdelay_Resp_Follow_Up` messages that are exchanged during the peer delay mechanism described in the [Propagation Delay Measurement process](01_propagation-delay-measurement.md).

The `pdelayRespEventIngressTimestamp` is generated locally when a `Pdelay_Resp` message is received. It represents the reception time of the event according to the `LocalClock` of the receiving device. It is a raw observation on the local time base before any frequency or offset correction is applied.

The `responseOriginTimestamp` is generated by the neighbor device when the `Pdelay_Resp` message is transmitted. It represents the transmission time of the event according to the neighbor `LocalClock`. This timestamp is not carried in the `Pdelay_Resp` message itself but is provided in the subsequent `Pdelay_Resp_Follow_Up` message.

The `correctionField` accounts for timing delays introduced while the message is processed in a device and forwarded inside the network. The `correctedResponderEventTimestamp` is derived from the `responseOriginTimestamp` and the `correctionField`.

The `neighborRateRatio` calculation compares how much time elapsed between two received `Pdelay_Resp` messages according to the local clock. It also compares how much time elapsed between the corresponding transmitted `Pdelay_Resp` events according to the neighbor clock, using the corrected timestamps.

If both elapsed times are identical, both clocks run at the same frequency. If the elapsed times differ slightly, the clocks run at slightly different frequencies.

## Relation to Time Synchronization

The `neighborRateRatio` is an important part of the gPTP syntonization process.

Before two devices can accurately synchronize their timestamps, they must first compensate for frequency differences between their local oscillators.

Without this correction, the propagation delay measurements would slowly drift. This would mean that the synchronization accuracy would continuously degrade and especially downstream (devices further away from the {{< tooltip "GM">}}) time-aware systems would accumulate timing errors.  
The `neighborRateRatio` therefore allows all time-aware systems in the gPTP domain to establish a common frequency basis before performing precise time synchronization.
